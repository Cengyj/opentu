# Change: Harden version upgrade convergence

## Why

The current staged-upgrade path can reach `upgradeState=ready` with an installed waiting worker while rendering no update prompt and sending no `COMMIT_UPGRADE`. A controlled Chromium reproduction proved that a persisted `processing` task fixture is sufficient to suppress the prompt even though the prompt listener and `version.json` request both ran. Persisted task status is not proof of a live executor, so stale or orphaned rows can hide an upgrade forever.

The release container also serves the SPA, Service Worker, version metadata, and hashed assets without `Cache-Control`. Byte-level checks proved that both production image domains were serving the same 1.0.1 build, so the observed upgrade trap is not explained by different deployed bytes. The final Docker layer uses a BusyBox static server and does not apply `apps/web/public/_headers`; browser convergence therefore depends on unspecified intermediary caching behavior.

Subsequent release-history inspection exposed a second identity defect: multiple distinct `v1.0.2-*` releases all advertised display version `1.0.2`, and at least two generated byte-identical `sw.js` files. The display/npm version was also used as the Service Worker state identity and `drawnix-static-v*` namespace. A corrected application bundle therefore could remain undiscoverable, while old image-routing model/endpoint evidence could continue influencing automatic protocol selection after a page eventually refreshed.

Upgrade correctness requires one end-to-end contract spanning readiness delivery, truthful execution ownership, explicit user approval, one-time commit, activation/reload convergence, container response headers, and production release gates.

## What Changes

- Add an authoritative version-upgrade convergence state machine that retains page-local pending-version readiness across early or late UI mounting and rejects stale asynchronous version reads.
- Separate human-facing/npm `version` from an immutable per-build `releaseId`, and carry the latter through HTML, `version.json`, Service Worker bytes/state, preload manifests, cache namespaces, commit identity, and release gates.
- Keep an update notice visible whenever a distinct pending version is ready; task conditions may affect available actions but MUST NOT silently remove all update UI.
- Classify upgrade blockers from typed execution evidence as `live`, `recovering`, `stale-orphan`, or `unknown-authority`: a consumed one-shot dispatch token needs matching local executor/session heartbeat evidence, while an acknowledged remote job uses a separate query-only polling lease. `unknown-authority` carries reason `storage-error`, `projection-unavailable`, or `inconsistent-state` instead of misreporting every unknown as storage failure.
- Treat a consumed dispatch whose heartbeat cannot currently be verified as `recovering` or `unknown-authority` rather than stale. Heartbeat or polling-lease expiry MUST NOT recreate submit authority or make a long synchronous provider request safe to interrupt for upgrade.
- Reconcile stale/orphaned task rows before upgrade and provide reason-specific UI for `unknown-authority`, including bounded retry only when its reason is `storage-error`.
- Preserve running work by default. Any "terminate tasks and upgrade" action requires separate explicit user approval and the approved cancellation contract.
- Send exactly one `COMMIT_UPGRADE` for each user-confirmed pending version, then let activation/controller change complete the already-approved reload without reapplying the old generic active-task guard.
- Preserve waiting-worker resolution and explicit confirmation; do not introduce unconditional `skipWaiting` plus `clients.navigate` behavior.
- Semantically supersede `fix-version-update-notification-delivery` while retaining its page-local readiness snapshot, mount-order parity, clear/replace ordering, and stale-fetch protection. The existing change remains untouched for audit history.
- Serve release-sensitive documents with explicit revalidation/no-store headers and only content-hashed assets with immutable caching.
- Replace the BusyBox final static layer with a pinned, testable Nginx/OpenResty-compatible container configuration rather than relying on hosting-specific `_headers` support.
- Register the Service Worker with `updateViaCache: 'none'` and fetch version metadata with `cache: 'no-store'`.
- Gate releases on container-direct plus public-domain checks for version identity, byte identity, and exact cache headers.
- Preserve prior release-scoped static caches while older tabs may still request their hashed chunks; remove the unconditional 30-second cache deletion and constrain lazy-chunk recovery to the currently committed static cache.
- Version image-routing discovery and endpoint evidence independently from the application release, automatically refresh stale evidence, coalesce same-identity discovery, fence superseded completions, scope pricing endpoints to an opaque credential identity, and prevent stale evidence from reaching automatic image planning while retaining Profiles, credentials, selected model IDs, pricing data, tasks, and generated artifacts.
- Document the unavoidable recovery path for already-running legacy pages, which future JavaScript cannot retroactively change.

## Impact

- Affected specs: version-upgrade-convergence (new), release-safe-static-loading, provider-routing
- Affected code: runtime-version state owner, bootstrap update handling, deferred VersionUpdatePrompt, typed task dispatch-heartbeat/query-lease projection, safe reload flow, Service Worker commit/activate handling and registration, version metadata fetches, Docker final stage, Nginx/OpenResty configuration, release verification scripts, automatic image-routing evidence readers/refresh, and operational runbooks
- User-visible result: an available update remains discoverable, accurately explains any `live`, `recovering`, or reasoned `unknown-authority` blocker, and converges after explicit approval instead of being hidden by stale task history
- Deployment result: both production domains and the container origin expose deterministic caching behavior for HTML, Service Worker scripts, release metadata, and hashed assets
- Data impact: no deletion of task history, images, generated artifacts, Profiles, credentials, or user IndexedDB data. Legacy Service Worker state is normalized at one read boundary. Stale routing evidence is ignored/refreshed without a destructive user-data migration.
- Compatibility impact: a page already executing old JavaScript cannot receive this behavior until it is refreshed; no proposal can rewrite an already-loaded bundle retroactively

## Verified Chromium Evidence

The controlled sequence produced these exact states:

- Initial v1.0.0: `navigator.serviceWorker.controller` and `registration.active` were both `activated`.
- After switching the server to v1.0.1: `committedVersion=1.0.0`, `pendingVersion=1.0.1`, `upgradeState=ready`, and the waiting worker was `installed`.
- With a `processing` fixture in `aitu-app/tasks`, the VersionUpdatePrompt listener ran and `version.json` was fetched, but prompt count was 0, update-button count was 0, and `COMMIT_UPGRADE` count was 0.
- After controlled explicit confirmation, the `COMMIT_UPGRADE` count was exactly 1.

The evidence distinguishes readiness delivery from visibility suppression: update readiness existed and the consumer executed, but the persisted task-status guard removed every user action.

## Verified Deployment Evidence

For both exact public origins:

- `https://image.forcodeai.xyz`
- `https://image.foropencode.com`

the responses for `/`, `index.html`, `sw.js`, `version.json`, and core content-hashed chunks were byte-for-byte identical and represented version 1.0.1. All checked responses lacked `Cache-Control`. The Docker final layer is a BusyBox static server, so `apps/web/public/_headers` is not applied by the running image.

No credential, API key, task payload, generated image, or base64 body is retained in this proposal.

## Supersession and Coordination

Upon approval, this change is the authoritative semantic replacement for `fix-version-update-notification-delivery`. It preserves that change's page-local pending-version snapshot, early/late mount equivalence, authoritative clear/replace behavior, and stale asynchronous fetch guard. It rejects only the earlier rule that `activeTasks` hides the prompt completely. The older change MUST NOT be implemented independently once this proposal is approved and remains unmodified until normal OpenSpec archival/coordination is separately authorized.

This change coordinates with:

- `refactor-image-task-lifecycle` for one-shot image dispatch facts, matching executor/session liveness, and separate query-only polling-lease facts
- `enforce-task-queue-concurrency-limit` for queue admission rather than upgrade visibility
- `fix-task-queue-external-cancellation` for any explicitly approved terminate-and-upgrade action
- `improve-version-update-interface-accessibility` for localization, focus, status announcement, and reduced motion
- `refactor-sw-duplex-comm` for transport mechanics without moving convergence ownership into an event bus
- `refactor-startup-shell-loading` for deferred UI budgets without returning the full prompt to the startup graph

## Approval Status

The user explicitly approved implementation of the non-destructive convergence scope: release identity, visible safe update state, commit/reload convergence, pinned container server and headers, release gates, retained prior static caches, and routing-evidence versioning/refresh. This approval does not include terminate-and-upgrade, unconditional `skipWaiting`, `clients.navigate`, deletion of user data, or any automatic forced legacy-client activation/navigation bridge.
