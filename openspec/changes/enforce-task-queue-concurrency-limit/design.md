## Context

- `task-queue-service.ts:1904-1963` 创建普通任务后直接调用私有 `executeTask()`。
- `useTaskExecutor.ts:193-229,565-578` 才读取 `AI_GENERATION_CONCURRENCY_LIMIT`，但只接管 `pending`、角色和恢复任务。
- MCP queue mode 可在一个同步循环中创建最多 10 个任务；批量 UI 和多个入口可叠加更多普通任务。
- 受控样本：Node 24.14.0、Vitest 3.2.4、无真实网络；21 个任务在同一 gate 内的执行峰值为 21，声明上限为 20。

## Goals / Non-Goals

- Goals:
  - 正常创建、重试和恢复任务使用同一并发计数口径。
  - 等待任务、运行任务和终态对 UI 可区分且可恢复。
  - 许可在成功、失败、取消、同步异常和组件卸载路径均释放一次。
- Non-Goals:
  - 不调整上限数值 20，不新增用户配置。
  - 不改变视频批量串行/并行正式规格。
  - 不把 ZIP、缓存、GitHub 或非模型请求纳入该许可池。

## Decisions

- Decision: 把许可所有权放在任务执行服务边界，所有入口在调用供应商前取得许可。
  - Alternative: 只把 `createTask()` 改成 `pending` 并继续依赖 React Hook。
  - Rejected because: 执行正确性不应依赖某个组件是否已挂载，且工作流/非 React 入口需要同一边界。
- Decision: 保留现有常量值 20。
  - Alternative: 根据供应商动态配置。
  - Rejected because: 当前没有配置契约或测量依据，属于新增产品行为。

## Invariants

- 同一任务最多执行一次；重试先清旧执行状态再重新排队。
- 任意时刻进入 AI/模型执行器的任务数不超过 20。
- 排队任务刷新后不会被错误标记为已提交到供应商。
- 参数、路由快照和大字段重试回灌保持不变。

## Risks / Trade-offs

- 任务开始时间相对当前会延后；UI 必须明确排队而非假进度。
- 两套现有执行入口合并许可时可能重复计数或漏释放。
- 恢复任务与新任务的公平顺序需要固定，避免饥饿。

## Migration Plan

1. 先补 21 个受控任务、取消排队任务、失败释放许可和恢复任务交错的红测试。
2. 在执行服务内建立单一许可/等待队列，移除或收敛 Hook 的重复并发计数。
3. 复验创建、重试、恢复、取消、超时、刷新和任务面板状态。

## Acceptance Thresholds

- 5 次独立受控样本中，每次 21 个任务的执行器峰值均 `<= 20`，第 21 个在释放许可前调用数为 0。
- 取消排队任务后供应商调用数为 0；失败/取消后后续任务 1/1 获得许可。
- 相关单测、typecheck、cycles、production build 和现有全仓基线无新增失败。
- 不提高并发、超时、bundle 或启动预算。

## Rollback

- 独立回退许可调度、排队状态映射和新增测试。
- 不迁移或清理 IndexedDB；已有任务记录保持可读。
